# EU AI Act features for 3.0.0

Issues: #336 (Art. 50 transparency), #339 (compliance report), #337 (Art. 5 prohibited practices). All three ship in 3.0.0, before release PR #346 merges.

## Intent

3.0 already strengthens AI.Sentinel's compliance story with redaction (GDPR data minimisation, Art. 10), the hash-chained audit log (Art. 12) and tool-call approvals (Art. 14). These three features complete it:

- **#336** helps deployers meet Art. 50 by telling people they are dealing with AI.
- **#339** turns the audit log into evidence an auditor can read.
- **#337** flags attempts to use the AI for practices Art. 5 prohibits.

AI.Sentinel provides building blocks, not a compliance verdict. Every user-facing text, including the docs, the README table and the report header, keeps the README's existing honest framing. Nothing claims that using a feature makes a system compliant.

## Global constraints

- **No original value leaks.** No feature writes message content, redacted values or personal data into audit entries, reports, logs or exceptions. Counts and codes only.
- **Audit format.** New audit entry kinds follow the redaction pattern:
  - a fixed `PolicyCode`;
  - `Severity.None`;
  - kept out of threat tiles, trend, risk score, threat metrics and alerts.
- **Audit hash rule.** Use existing `AuditEntry` fields only; no new hashed fields. If a new field is ever needed, follow the documented rule in `AuditHashChain`.
- **Additive API.** Public API is additive, except the new `DetectorCategory.Compliance` value, which 3.0 allows. New options are init or settable properties, never new positional parameters.
- **Build hygiene.** Analyzers run as errors; the AOT and trim analyzers stay clean; `dotnet format whitespace --verify-no-changes` passes.
- **Commits.** One PR per feature. Commit type `feat:`. Bodies have no nested parentheses, and no body line starts with a conventional type followed by a colon.

## 1. Art. 50 transparency (#336)

### Who and why

Art. 50 asks that people are told when they interact with an AI system, and that AI-generated content is marked in a machine-readable way.

- **Who uses it:** a company building a chatbot or assistant on AI.Sentinel's `IChatClient` middleware.
- **Who checks it:** regulators, auditors and privacy officers want proof that disclosure happened.

### Decided with the maintainer

- **Off by default.** One option turns it on, so there is no behaviour change for existing users.
- **Machine-readable mark on every reply.**
  - Placed in `ChatResponse.AdditionalProperties`: AI-generated flag, model id (`ChatOptions.ModelId`, available since #390), timestamp, pipeline name.
  - Streaming replies carry the same mark.
- **Model id in the mark:** prefer `ChatResponse.ModelId`, the model that actually answered, and fall back to `ChatOptions.ModelId` (my call, after review).
- **Optional human-readable notice.**
  - The text is configurable; the default is "This answer was generated by AI."
  - It is added **once per conversation** by default, on the first reply in a session (session ids since #350).
  - The app can choose **every reply** instead, or **never** if its own UI already discloses.
- **Proof in the audit log.** An informational `DISCLOSED` audit entry, used by the compliance report.
- **In-process client only.** The Claude Code / Copilot hook CLIs and the MCP proxy are out of scope: those tools have their own UI, and the model's reply does not pass through Sentinel there.

### Design (builder's calls marked "my call")

**Options.**

- `SentinelOptions.Transparency`, a `TransparencyOptions` instance with these members:
  - `Enabled` (bool, default false).
  - `Notice` (string, default "This answer was generated by AI.").
  - `NoticeMode`: `OncePerConversation` (default), `EveryReply` or `Never`.
- Validation rejects an empty `Notice` when the mode is not `Never`.

**Metadata keys** (my call). Lower-case, namespaced, documented:

| Key | Value |
|---|---|
| `ai.generated` | `true` |
| `ai.model_id` | the model that answered, or absent |
| `ai.generated_at` | ISO 8601 UTC |
| `ai.pipeline` | the pipeline name for named pipelines, or absent for the default |

- **Streaming:** the keys go on the first update, so `ToChatResponse` carries them. The builder verifies that MEAI 10.11 merges update `AdditionalProperties` and otherwise picks the update that does.
- **Existing values:** values the inner client set are never overwritten. If a key already exists, Sentinel's value wins only for `ai.generated`.

**Which reply is disclosed** (my call, after review). A reply counts only when it carries text the person sees.

- A response made only of tool calls is not disclosed, so no notice and no `DISCLOSED` entry.
- With Sentinel inside function invocation, every model round trip is its own call. The notice and the entry land on the first round trip whose response has assistant text.
- With Sentinel outside function invocation, the notice goes on the final assistant text message of the returned response, not on an intermediate tool-call message.
- The audit never claims a disclosure the person did not see.

**History** (my call, after review). Apps send earlier replies back as history. Before scanning and forwarding, Sentinel removes its own notice from incoming assistant messages. The match is an exact one: the configured `Notice` text as the leading `TextContent` it added. The notice is never re-scanned, never sent to the model, and never piles up in every-reply mode.

**Notice placement** (my call).

- The notice is prepended as its own leading `TextContent` in the first assistant message, followed by a blank line. Disclosure comes before the content.
- In streaming, it is emitted as text at the start of the first text update.
- It is added **after** the response scan and **after** redaction restore, so detectors never judge it and it is never mistaken for model output.

**"Once per conversation".**

- An in-memory set of session ids that have already seen the notice, scoped per pipeline.
- Entries are evicted after `SentinelOptions.SessionIdleTimeout`, as the rate limiter and alert dedup already do.
- Without a session key, every call is its own session, so the notice appears on every reply. This is documented, along with how to pass `sentinel.session_id` or `ConversationId`.
- In multi-instance deployments each instance tracks its own set. That is documented as a known limit.

**Audit.**

- One `DISCLOSED` entry per session per pipeline, written the first time a reply in that session is marked.
- The `Summary` says which disclosure applied, for example `Disclosed: machine-readable mark and notice` or `Disclosed: machine-readable mark` when the mode is `Never`.
- `DetectorId` is `TRANSPARENCY`. The rest follows the redaction-entry pattern: `PolicyCode = "DISCLOSED"`, `Severity.None`, the dashboard badge and chip, and Information level in OpenTelemetry.
- The entry is written when the reply is returned, not when it is requested.

**Failure.** A reply that fails (quarantine, pipeline failure) gets no mark, no notice and no entry.

**Docs.**

- A website page.
- The README EU AI Act table Art. 50 row moves from "Not covered" to "⚠️ partial: opt-in machine-readable mark and notice in the in-process client; the hook CLIs and MCP proxy are out of scope".

## 2. Compliance report (#339)

### Who and why

The person who must show an auditor, privacy officer or regulator that the safeguards actually ran, not just that they were configured.

### Decided with the maintainer

- **Command.** `sentinel report` in the existing `AI.Sentinel.Cli` (`sentinel` tool), next to `sentinel dashboard`.
- **Input.** It reads the audit SQLite file; `--db` defaults to the same file as the dashboard. A later decision dropped `--approvals-db`; see Design.
- **Options.**
  - `--from` and `--to` set the period, defaulting to the last 30 days.
  - `--format` takes `md` (the default), `html` or `json`.
- **Sections by EU AI Act article:**
  - **Art. 12:** chain integrity, entries, period, sources.
  - **Art. 14:** policy denials, and approvals granted, denied or expired, from the audit log.
  - **Art. 10 / GDPR:** redaction counts by type.
  - **Art. 50:** conversations disclosed.
  - **Art. 15:** detections per detector and severity, top detectors.
  - **Art. 5:** the compliance detectors from #337.
- **Header.** Period, generation time, the audit file, and the honest "building blocks, not a verdict" note.
- **Read-only and offline.** It never modifies the audit file.
- **Totals only.** Per-session drill-down stays in the dashboard.

### Design (builder's calls marked "my call")

- **`--output`** (my call): writes to a file instead of stdout. The exit code is 0 on success, non-zero on unreadable input, and a distinct non-zero code when the chain is broken, so CI or scheduled jobs can alert.
- **Chain verification** runs over the **whole** audit file, not just the period, because the chain is global. The report shows intact or not, the entries checked, and the first broken entry id. Retention trimming legitimately removes the oldest entries; the builder confirms `AuditHashChain.VerifyAsync` handles a trimmed head and says how in the report.
- **Counts come from audit entries only:**
  - redactions: `REDACTED` summaries parsed for type counts;
  - disclosures: distinct sessions with `DISCLOSED`;
  - denials: `AUTHZ-DENY`;
  - detections: everything else, by `DetectorId` and `Severity`;
  - fallbacks: entries ending in `; not redacted`, counted separately.
- **Approvals** (decided with the maintainer after review): approval stores delete a request once it is settled, so the approvals database cannot show what was granted or denied.
  - Every approval decision therefore writes an informational, hash-chained audit entry, following the redaction pattern, with `Severity.None` and kept out of the threat counts.
  - The decisions covered are approved, denied, expired, and timed out while waiting.
  - This applies wherever a decision is made: the dashboard approve and deny endpoints, the SQLite and in-memory stores when they observe expiry, and the Entra PIM store when it observes the PIM outcome.
  - Each entry carries a fixed `DetectorId` such as `APPROVAL` and a `PolicyCode` of `APPROVED`, `DENIED` or `EXPIRED`.
  - The `Summary` gives the policy and tool names only: no arguments, no approver note, no caller id. The approver's id stays in the approval store, as today.
  - The report reads only the audit file. The `--approvals-db` option is dropped.
  - This is part of the #339 work and lands before the report.
- **Article mapping** (my call):

| Section | Contents |
|---|---|
| Art. 5 | `CMP-*` detections |
| Art. 10 / GDPR | redactions and fallbacks |
| Art. 12 | chain, volume, sources, retention note |
| Art. 14 | denials and approval decisions |
| Art. 15 | all other detections |
| Art. 50 | disclosures |

  A section with nothing to show says so and explains what would populate it, for example "no approvals database given".
- **Output never contains** message text, detection `Summary` text (it can quote content), session ids or caller ids. Only counts, detector ids, severities, policy codes and entry ids.
- **HTML** is a single self-contained file with no external assets, printable, and with a light theme only (my call).
- **JSON** has a documented, versioned shape (`"schema": 1`).
- **Docs:** a website page with a sample report and the README EU AI Act intro mentioning the report.

## 3. Art. 5 prohibited practices (#337)

### Decided with the maintainer

- **Detectors.** Four detectors in a new **Compliance** category (`DetectorCategory.Compliance`), IDs `CMP-01` to `CMP-04`:

| ID | Practice | Example |
|---|---|---|
| `CMP-01` | Social scoring | rating or classifying people by social behaviour or personal traits in a way that leads to worse treatment |
| `CMP-02` | Emotion recognition in the workplace or in education | inferring the emotions of employees or students |
| `CMP-03` | Biometric categorisation of sensitive traits | race, religion, political views or sexual orientation from photos, voice or other biometric data |
| `CMP-04` | Predicting crime from profiling | from personality or profile alone |

- **Out of scope:** subliminal manipulation, exploiting vulnerabilities, untargeted facial-image scraping and real-time remote biometric identification.
- **Semantic detectors** (embedding similarity to example phrases, like `GovernanceGapDetector`). They need an embedding generator, and the docs say so plainly.
- **Default severity High**, so the default action is Alert, not a block. Per-detector `Action` can raise it to Quarantine.
- **Both scan legs**, request and reply.

### Design (builder's calls)

- **False-positive evidence** (decided with the maintainer after review). `FakeEmbeddingGenerator` compares shared two-character fragments, so it measures wording, not meaning. Fake-generator unit tests cover the wiring only.
  - Before shipping, run a one-off evaluation of every positive example and a set of legitimate near-misses through a real embedding model. A local model is preferred, for example a small sentence-embedding model through ONNX Runtime; otherwise any real provider the builder can reach.
  - Write the results up in the PR: the model, the similarity per phrase, and the chosen thresholds.
  - Set each detector's threshold from that data.
  - Commit the evaluation as a re-runnable tool or test project outside the default test run, with its input phrases.
  - If no real model can be run in the build environment, stop and report rather than ship untuned.
- **Examples.** Each detector extends `SemanticDetectorBase` with high-similarity examples. The builder writes realistic positive examples per detector, and near-misses for the evaluation:
  - wellbeing surveys;
  - aggregate, anonymous sentiment;
  - accessibility features;
  - a doctor discussing a patient's mood;
  - legitimate credit checks on financial data.
- **No rule-based fast path** (my call), because these are intent detectors and a keyword path would be noisy.
- **Every detector-count and category touch point is updated:**
  - README detector table and the "56 detectors" counts;
  - website detector pages, with a new `website/docs/detectors/compliance.md`;
  - `DetectorDocumentationTests`;
  - the `McpPipelineFactory` detector-count drift guard and MCP presets (include CMP detectors in the presets that include semantic security detectors; the builder states the choice);
  - dashboard category chips (add Compliance; exclude REDACTED and DISCLOSED rows as today);
  - OWASP mapping tables: no OWASP row.
- **README EU AI Act table:** add an Art. 5 row stating what is covered, that an embedding generator is needed, and the default Alert action.

## Order and release

Build in the order #336, #339, #337. The report has sections for the other two, so it lands after #336 and its Art. 5 section is filled once #337 lands. #337 can also go before the report; the builder adjusts the report's Art. 5 section to whatever exists.

Each feature is its own PR from `main`. Then #346 releases 3.0.0.

## Testing expectations

- **#336:**
  - mark on every reply, both normal and streaming;
  - notice once per session, every reply, or never;
  - no notice or mark on a quarantined reply;
  - notice not scanned and not restored;
  - one `DISCLOSED` entry per session;
  - eviction after idle;
  - existing `AdditionalProperties` not overwritten.
- **#339:**
  - approve, deny and expire each write one approval audit entry with no argument or caller text;
  - each section from a seeded audit file;
  - a broken chain gives the distinct exit code and the first broken id;
  - no `Summary`, session or caller text appears in any output;
  - all three formats;
  - an empty period;
  - approval entries counted per outcome.
- **#337:**
  - each detector fires on its examples and stays clean on the near-misses, with the fake embedding generator;
  - detector docs and count tests updated;
  - Compliance category in DI and dashboard.
