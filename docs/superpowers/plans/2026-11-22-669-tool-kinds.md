# Map each CLI's tools onto shared tool kinds, with a shell parser (#669) Implementation Plan

**Goal:** A policy should not need one rule per CLI for the same kind of tool. The hook CLIs map each CLI's own tool onto a shared tool kind and hand the policy the kind's details, so one rule covers `Bash` in Claude Code, the shell tool in Copilot CLI and the one in Codex (ADR-235). This issue builds that input; #654 evaluates policy against it.

**Issue:** #669, milestone "Controlled from a central server".

**Spec:** Outline document `6888019f-3202-4ea3-93a7-213cc8811bf0` ("AI.Sentinel: be controlled from Themis.NET") and its approved design, Outline document `b4b02d34-d3a1-4141-b5a0-4d51bcba7d91` ("AI.Sentinel: central server control, design", Status: approved). Read both with the Outline connector before writing code. Where they differ, the design wins; where the design and an accepted ADR differ, the ADR wins. #653 and #657 are replaced by the design and are not a source.

## Acceptance criteria

From the issue. Each has a test or check named after it.

- Each tool of Claude Code and Copilot CLI maps to one kind: `shell`, `read`, `search`, `write`, `edit`, `fetch`, `mcp`, `agent` or `other`. A tool the mapping does not know is `other`. `ToolKindMappingTests`.
- The policy input carries `kind`, `cli` (`claude-code`, `copilot`, later `codex`), the CLI's own tool name, the kind's details, `findings` (`detector`, `severity`), `repository`, `node` and `session`. Fields that later issues fill (`repository`, `node`) are present and empty until then. `PolicyInputTests`.
- For `shell`, the command line is parsed into commands and arguments, including pipes, `&&`, `||`, `;` and quoting. A command line the parser cannot parse is marked unparseable, and the outcome for it is **ask** (#670). `ShellCommandParserTests`.
- For `mcp`, the details are server, endpoint and tool. For the file kinds, each path is given with a flag for whether it lies inside the repository. `PolicyInputTests`.
- A test corpus of command lines with their expected parse lives in the repository, and the parser runs against all of it in CI, so a later parser (for example the server's) can be checked against the same corpus. `ShellCommandParserTests`.
- The input is built without runtime reflection and the hook CLIs still publish under Native AOT without warnings. AOT publish check.
- With none of the new settings, the hooks behave exactly as before: nothing reads the input yet. Existing suite.
